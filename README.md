# Projectyard: похорони репозиторий

Сайт перед запуском основного Projectyard. Человек вставляет ссылку на заброшенный репозиторий, проходит сцену похорон и получает свидетельство о смерти, которым можно поделиться. Когда наберётся 100 проектов, начнём разработку основного сайта, и все похороненные здесь проекты переедут туда.

Портфолио, которое раньше лежало в этом репозитории, сохранено в ветке `portfolio`.

**Стек:** Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS 4, Motion, Supabase, next/og для картинок.

## Как это устроено

1. `/` — форма. Сервер по ссылке забирает у GitHub дату создания, число коммитов и последний коммит. Пользователь выбирает причину смерти, пишет эпитафию и указывает свой ник на GitHub (обязательно). Ник запоминается в браузере: в следующий раз он уже в поле, а ссылка начинается с `https://github.com/<ник>/`.
2. «Похоронить» запускает сцену `src/components/funeral-scene.tsx`: prep → coffin → lowering → burying → silence. До silence похороны можно отменить, в базу ещё ничего не записано. На silence могила сохраняется, сцена гаснет в темноту, и страница свидетельства проявляется из той же темноты.
3. `/r/<owner>/<repo>` — свидетельство и кнопки под ним. «Поделиться» на телефоне открывает системное меню с картинкой для сторис, на компьютере — попап (`src/components/share-dialog.tsx`): текст поста, Telegram, X, ВКонтакте, Reddit, LinkedIn, Threads (в английской версии вместо ВКонтакте Bluesky), копирование ссылки, текста и картинки, скачивание PNG. Соцсети открываются по их собственным ссылкам для публикации, без SDK и сторонних сервисов. После сцены свидетельство появляется с раскрытием, при переходе по ссылке — сразу.
4. `/r/<owner>/<repo>/certificate.png` — картинка 1200×630. Её же соцсети прикрепляют к ссылке (og:image). `?format=story` — 1080×1920 для сторис, `?download` — отдаёт файлом.
5. В шапке счётчик «N/100 проектов», по клику попап про основной сайт, и переключатель языка.

Всё то же самое есть на английском по адресам с `/en`, см. «Языки».

Один репозиторий хоронят один раз: повторная ссылка ведёт на существующее свидетельство. Свидетельства живут только в базе, поэтому подделать их ссылкой нельзя.

## Supabase

Без базы сайт не работает: для запуска, в том числе локально, нужны ключи Supabase.

1. В SQL Editor проекта основного Projectyard выполнить по очереди `supabase/migrations/0001_bury.sql`, `0002_store_less.sql` и `0003_bury_log.sql`. Все миграции можно запускать повторно, поэтому неважно, какие уже выполнялись.
2. Задать переменные окружения (см. `.env.example`). На Vercel — для Production и Preview, затем Redeploy: уже собранные деплои новых переменных не видят.

| Переменная | Зачем |
| --- | --- |
| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | Запись и чтение могил. Ключ используется только на сервере |
| `SITE_URL` | Адрес сайта для ссылок и og:image. Без него берётся из заголовков запроса |
| `NEXT_PUBLIC_TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY` | Невидимая проверка на бота Cloudflare Turnstile, см. «Защита от накрутки». Без них выключена |
| `GITHUB_TOKEN` | Fine-grained personal access token с доступом «Public repositories (read-only)» и без прав. Без него GitHub даёт 60 запросов в час на IP, а IP у Vercel общие, так что на проде он нужен. С токеном 5000 в час |

Строки с этого сайта помечены `source = 'bury'`, счётчик считает только их.

Проверить подключение: открыть `/api/health` на нужном деплое. `ok` — база отвечает, `error` — текст ошибки: деплой не видит ключей, база не отвечает или не выполнена миграция. `botCheck` — включена ли проверка на бота.

### Защита от накрутки

Похоронить можно без входа, поэтому счётчик защищён так:

- **Лимит по IP:** не больше 3 похорон за 10 минут и 10 в сутки с одного адреса (`BURY_LIMITS` в `src/lib/config.ts`). Считается по таблице `bury_log`, где лежит только HMAC-хеш IP, сам адрес не хранится. Таблица закрыта от публичного ключа. Проверок ссылки — не больше 30 в минуту: каждая стоит запросов к GitHub.
- **Известные проекты не хоронятся:** больше 1000 звёзд (`FAMOUS_STARS`) — это не заброшенный пет-проект, а вероятный троллинг.
- **Cloudflare Turnstile:** невидимая проверка, что похороны пришли из настоящего браузера. Бесплатно:
  1. Cloudflare → Turnstile → Add widget. Hostnames: домен сайта и `vercel.app` для превью. Widget Mode: Managed.
  2. В Vercel задать `NEXT_PUBLIC_TURNSTILE_SITE_KEY` (Site Key) и `TURNSTILE_SECRET_KEY` (Secret Key) для Production и Preview, затем Redeploy.
  3. Проверить: в `/api/health` должно быть `"botCheck":"on"`.

  Если Cloudflare не отвечает, похороны пропускаются без проверки, лимит по IP всё равно работает.
- **Модерация:** неудачную запись можно удалить в Supabase → Table Editor → `projects`. Счётчик пересчитается сам.

### Что хранится, а что считается

В `projects` лежит снимок репозитория на момент похорон и то, что ввёл человек. Свидетельство — документ: если репозиторий потом переименуют или удалят, оно не изменится.

| Хранится | Откуда |
| --- | --- |
| `id` — он же номер участка, `created_at` — дата похорон | база |
| `repo_id` — id репозитория на GitHub, не меняется при переименовании; `repo_owner`, `repo_name` | GitHub |
| `born_at`, `died_at` (последний коммит), `commits`, `last_words` (текст последнего коммита) | GitHub, для свидетельства |
| `description`, `language`, `topics`, `license`, `stars` на момент похорон | GitHub, для каталога на основном сайте |
| `cause`, `epitaph`, `buried_by`, `adoptable`, `variant` | форма |
| `slug` = lower(owner/name) | считает сама база |

Не хранится, считается при показе:

- сколько проект прожил и сколько лежит без коммитов, склонения, формат дат, номер участка вида «№ 0007»;
- ссылка на репозиторий и аватар владельца — из `repo_owner` и `repo_name`;
- картинка свидетельства и og:image — рисуются из строки по запросу, их кэширует CDN;
- счётчик «N/100» — `count` по `source = 'bury'`.

Живые данные для страницы проекта на основном сайте (звёзды сейчас, архивирован ли, удалён ли, «воскрес» ли — были ли коммиты после `created_at`) тоже лучше брать у GitHub при заходе, по `repo_id`, с кэшем на час. В базу их стоит писать, только если по ним понадобится фильтровать каталог.

Привязка к аккаунту на основном сайте: там вход через GitHub и таблица `profiles` с `github_username`. Когда человек войдёт, его проекты находятся по `repo_owner`, тогда же можно добавить `user_id` и подтверждать галочку «можно передать».

## Деплой на Vercel

Импортировать репозиторий, задать переменные выше, `SITE_URL` — боевой домен. Шрифты для картинок читаются из `node_modules/@fontsource` и попадают в сборку через `outputFileTracingIncludes` в `next.config.ts`.

## Варианты свидетельства

Оформление лежит в `src/certificate/variants`. Сейчас есть один вариант, `classic`. Один и тот же компонент рисует свидетельство на странице, в превью ссылки и в скачиваемом PNG.

Чтобы добавить вариант:

1. Создать `src/certificate/variants/<id>.tsx`, экспортировать объект `CertificateVariant` с `render(data, format)` для форматов `card` и `story`.
2. Дописать его в массив `variants` в `src/certificate/variants/index.ts`.
3. Выбор оформления в форме появится сам. Выбранный id сохраняется в `projects.variant`.

Пока вариант не готов, его можно смотреть на настоящих данных: `/r/<owner>/<repo>/certificate.png?variant=<id>`.

Картинки собирает Satori, поэтому в разметке варианта только flex-вёрстка и инлайн-стили, у каждого `div` с несколькими детьми явный `display: flex`, без CSS-переменных и без текста внутри `<svg>`. Шрифты берутся из `typeface` в `src/certificate/typography.ts`.

С прошлого макета остались идеи ещё для двух вариантов: «надгробие и лог» и «бумажный бланк».

## Языки

Русский — основной, его адреса без префикса: `/`, `/r/<owner>/<repo>`. Английский — с префиксом: `/en`, `/en/r/<owner>/<repo>`, `/en/r/<owner>/<repo>/certificate.png`. Язык по браузеру не угадывается: у каждой страницы один адрес на каждом языке, так их правильно индексируют поисковики. Переключатель в шапке ведёт на ту же страницу на другом языке.

- Страницы лежат в `src/app/[lang]`. `src/proxy.ts` внутренне переписывает русские адреса на `/ru/…`, а `/ru/…` из адресной строки ведёт редиректом на адрес без префикса.
- Все тексты — в словарях `src/i18n/ru.ts` и `src/i18n/en.ts`: интерфейс, ошибки, причины смерти, эпитафии-заготовки, подписи на свидетельстве, пост для шеринга, метаданные. Склонения и формат дат там же.
- В базе язык не хранится: причина смерти лежит как id (`better`, `burnout`…), подпись берётся из словаря. Поэтому любое свидетельство открывается на обоих языках, эпитафия остаётся такой, как её написали.
- Серверные компоненты берут словарь через `dictionary(lang)`, клиентские — через `useI18n()` из `src/i18n/client.tsx`.
- В метаданных каждой страницы `hreflang` на обе версии, в `sitemap.xml` тоже обе. Превью главной — `/og.png` и `/og.png?lang=en`.

Чтобы добавить язык: словарь `src/i18n/<код>.ts` по образцу `en.ts`, код в `langs` в `src/i18n/index.ts`, код в первой проверке `src/proxy.ts`. Переключатель в шапке сейчас рассчитан на два языка.

## Картинки

`public/images` — картинки из основного Projectyard (репозиторий gravejects): логотип, луна с вороном на первом экране, кладбище на фоне сцены и свидетельства, пустое надгробие в сцене похорон, текстура камня. На странице они идут через `next/image`, в PNG свидетельства — как data URI (`src/certificate/server-assets.ts`).

## Промо-ролик

В `video/` — ролик для соцсетей в духе запусков Notion и Linear: 1920×1080, 30 fps, около 35 секунд. Сделан на [Remotion](https://www.remotion.dev): это React, поэтому свидетельство в ролике — тот же компонент, что на сайте, а картинки берутся из `public/images`.

```bash
cd video
npm install
npm run studio   # предпросмотр и правки в браузере
npm run render   # out/projectyard-launch.mp4
npx remotion render src/index.ts Launch out/projectyard-launch.mp4 --props='{"site":"projectyard.example"}'   # с адресом сайта в финале
```

Сцены: коммит «доделаю на выходных» → стена мёртвых репозиториев → логотип → работа с сайтом (ссылка, причина, эпитафия) → похороны → свидетельство и телефон со сторис → «Каждый проект заслуживает покоя».

| Что | Где |
| --- | --- |
| Тексты и пример репозитория | `video/src/copy.ts` |
| Длительность сцен | `video/src/timeline.json` (его читают и анимация, и звук) |
| Звуки и их громкость | `video/sound/build.mjs`, раздел «Партитура» |
| Сами сцены | `video/src/scenes/` |

Звук синтезируется кодом, без сэмплов: `video/sound/build.mjs` собирает `soundtrack.wav` из шума, синусов, фильтров и ревербератора по тем же таймингам, что и анимация (`video/src/timeline.json`). Звучит только то, что происходит в кадре: тихая печать в духе клавиатуры айфона, клики мыши, стук гроба, скрежет, сыплющаяся земля, удары резца. На сменах сцен и на нескольких главных надписях — тихий свист воздуха. Фона, музыки и низких ударов нет. `npm run render` сначала пересобирает звук, отдельно — `npm run sound`. Музыку при желании можно подложить поверх при публикации.

Remotion бесплатен для частных лиц и команд до трёх человек.

## Telegram-бот

Бот живёт внутри сайта (`src/bot`, маршруты `/api/telegram` и `/api/cron/posts`). Управляет им только `OWNER_TELEGRAM_ID`, а обычным людям он даёт узкий набор возможностей (см. «Для обычных людей» ниже). Что умеет владелец:

- **Жалобы.** Обращения «удалить или пожаловаться» с сайта (таблица `reports`) с кнопками «Готово», «Отклонить» и «Удалить могилу» (с подтверждением). О новом обращении бот пишет сам.
- **Календарь продвижения** (`src/bot/schedule.ts`, 14 дней, время по Москве). Посты «в канал» публикует сам в `TELEGRAM_CHANNEL_ID`, для остальных площадок присылает в личку готовый текст с ссылкой и меткой `utm_source`. В текстах подставляются цифры из базы (`{count}`, `{top_cause}`, `{mine_name}` и другие, см. `src/bot/stats.ts`). Если для подстановки нет данных, пост в канал не уходит, бот сообщает об этом.
- Команды: `/next` (ближайшее), `/post <id>` (предпросмотр, «опубликовать сейчас»), `/stats`, `/whoami`.
- **Оформление.** Сообщения бота в HTML: заголовки, цитаты, шкала прогресса; готовые тексты для ручных постов лежат в блоках кода, по нажатию на блок Telegram копирует весь текст. Посты в канал выходят с обложкой: файлы в `public/promo/` (нарисованы через agy), подключаются полем `photo` в `src/bot/schedule.ts` (`{site}/promo/имя.jpg`). Описание и «О боте» в профиле записывает `npm run bot:webhook`; аватарку задают у `@BotFather` командой `/setuserpic`.

**Для обычных людей** (`src/bot/user.ts`): человек присылает боту ник на GitHub и видит свои могилы (репозиторий его или похоронил он), может отправить запрос «убрать» (не больше 3 в сутки) и смотреть статус своих обращений. Ник не проверяется, поэтому по нему показываются только публичные данные и обращения, которые человек подал сам; в карточке запроса владельцу написано, совпадает ли ник с владельцем репозитория. Ответы приходят человеку в Telegram: при «Готово», «Отклонить», «Удалить могилу», а также обычным ответом (reply) владельца на карточку. С формы на сайте человек привязывает чат кнопкой «Получить ответ в Telegram» (ссылка `t.me/бот?start=r_токен`, токен одноразовый). Без привязки ответить некому, остаётся поле «контакт».

Настройка:

1. Создать бота у `@BotFather`, добавить его администратором канала.
2. Выполнить `supabase/migrations/0004_reports.sql`, `0005_bot_posts.sql` и `0006_bot_users.sql`.
3. Задать переменные из `.env.example` (раздел «Telegram-бот») в Vercel и сделать Redeploy. `OWNER_TELEGRAM_ID` подскажет сам бот по команде `/whoami`.
4. Зарегистрировать адрес бота у Telegram: в `.env.local` положить `TELEGRAM_BOT_TOKEN` и `TELEGRAM_WEBHOOK_SECRET`, затем `npm run bot:webhook -- https://адрес-сайта`.
5. В GitHub: Settings → Secrets and variables → Actions: секрет `CRON_SECRET` (тот же, что в Vercel) и переменная `SITE_URL`. Workflow `.github/workflows/promo-cron.yml` раз в 15 минут вызывает `/api/cron/posts`.
6. Пока `PROMO_START_DATE` не задан, бот ничего не отправляет. Для пробного прогона поставить `BOT_DRY_RUN=1`: посты «в канал» придут вам в личку предпросмотром.
